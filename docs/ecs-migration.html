Migrating OpenTTD to an EnTT registry

A phased plan for moving performance-critical systems onto an entity-component architecture — without breaking the save format, and leaving the game playable at every stop.

Status phases 0–6 done, three dispatch variants measured Target win64 only Library EnTT 3.16.0 (vcpkg) Baseline master @ 3a33cd64c9

Verdict: yes for targeted extraction, no for wholesale conversion

OpenTTD is an unusually good teaching subject, because it has already independently invented half of an ECS and then stopped. The pool system in src/core/pool_type.hpp is a slotmap: stable integer handles (PoolID), O(1) lookup by index, a free-slot bitmap, and iteration that walks live entries in ascending index order. That is the entity half, and it is genuinely good.

What it lacks is the component half. Vehicle is a single struct carrying roughly ninety fields, an embedded VehicleCargoList, an embedded Order, three separate cache sub-structs, six intrusive pointers, a vtable, and Money accounting fields — all resident whether or not the current operation touches them. The per-tick loop reads perhaps twenty bytes of that object.

So the win is real and locatable. But a full conversion is not on the table: Vehicle is referenced from 281 files by 1051 raw Vehicle * declarations, and the save format is bound field-by-field to its member layout. The workable shape is a parallel registry that holds hot data alongside the existing pool, with hot loops moved over one at a time.

The single most telling detail is inside CallVehicleTicks(): it calls virtual bool Tick() on every vehicle, then immediately runs a switch (v->type) over the same object. Virtual dispatch and a type switch, per vehicle, per tick. That is a textbook ECS target sitting in plain sight.

It was a textbook target and it was worth nothing. Phase 6 removed the virtual dispatch and measured zero change on both fixtures, then replaced the whole loop with typed passes and measured a 4% loss. The paragraph above is kept because it is the single most confident claim on this page and the clearest thing measurement has overturned. Diagnosing a hot loop by reading it finds what is ugly, not what is expensive.

Three constraints that shape everything

These are not style preferences. Each one eliminates specific EnTT features, and getting them wrong produces bugs that only appear in multiplayer or on reload — the worst possible failure mode to debug.

1. Canonical iteration order

OpenTTD needs two kinds of determinism. Every client must evolve the game state identically, and a savegame resumed must evolve identically to a run that was never saved — the second is what makes desync replay and mid-game joins work at all.

Today's pool iteration satisfies both trivially: PoolIterator visits live entries in ascending index order, which is a pure function of the live set and carries no history. EnTT's packed-array order is the opposite — it is a function of the entire create/destroy history, because swap-and-pop moves the last element into each hole.

Two specifics, both now pinned down by tests in src/tests/entt_smoke.cpp so that an EnTT upgrade which changed either one fails loudly rather than silently desyncing. Writing those tests immediately caught a wrong assumption, which is the best possible argument for writing them first:

OperationIteration order
Create ids 0–7, remove nothing7, 6, 5, 4, 3, 2, 1, 0
… then destroy id 26, 5, 4, 3, 7, 1, 0
… then sort ascending0, 1, 3, 4, 6, 7

So views walk the packed array backwards — iteration is not creation order even before history enters the picture. And after a single removal there is no canonical order at all: neither ascending, nor the descending order an untouched registry would have given.

The failure this produces

The savegame stores the live set, not the allocation history. Load a save and EnTT's packed order is fresh and sequential; in the run that produced that save it was scrambled. Any loop whose result depends on visit order then diverges — and in OpenTTD several do, because Random() is a single shared LCG. If vehicle A draws before B instead of after, both get different numbers, and the game states separate immediately.

Rule: any storage that game-state code iterates must be sorted into canonical ID order before use. Call registry.sort<T>() keyed on the stable ID, gated on a dirty flag set by create and destroy. Once sorted the storage is contiguous in ID order, so you keep the locality you came for.

Measured, and the assumption was half wrong. This originally continued "structural churn is rare next to the tick rate, so this amortises to nearly nothing", flagged here as load-bearing and unverified. Phase 6 measured it. On wentbourne the assumption holds handsomely — the registry is dirty on 2.6% of ticks and the sort costs 0.14% of the game loop. On Hilbergen it fails: dirty on 88% of ticks, at 10.4% of the game loop. The 30× smaller save is 74× more expensive in relative terms, because sort cost is set by churn frequency — a property of the savegame, not of its size. The O(n log n) barely enters into it. See phase 6.

Usefully, sort arranges storage so that iteration matches the comparator rather than the raw packed layout — a plain lhs < rhs yields ascending iteration despite the reversed walk. That reproduces PoolIterator's order exactly, which is what makes an order-preserving migration possible at all.

The mechanism, verified in EnTT's source rather than inferred from behaviour: iteration walks the packed array backwards (begin() is iterator{packed, packed.size()} and operator* reads packed[offset - 1]), while sort_n sorts through reverse iterators, leaving the array physically descending. Walking a descending array backwards yields ascending order, so the two reversals cancel by design. EnTT specifies sort in terms of iteration order, not physical layout.

Where the reversed walk still bites

It is invisible as long as you sort, and leaks the moment you iterate unsorted storage. That makes it a live trap for phase 2 specifically, where the client-side components deliberately do not need sorting: code there must not assume creation order.

Consequence: owning groups are unavailable for game-state components. EnTT forbids sorting a pool once a group owns it, and sorting is exactly what you need. Use views, or non-owning groups.

2. Pointer stability

EnTT's default swap-and-pop invalidates references on removal — and sorting moves components too, so switching a storage to in_place_delete does not rescue you. In fact it is not merely insufficient but unavailable, because sort_n opens with:

ENTT_ASSERT((mode != deletion_policy::in_place) || (head == max_size),
            "Sorting with tombstones not allowed");

So pointer stability via in_place_delete and canonical order via sort are mutually exclusive for any storage that game-state code iterates — and canonical order is not negotiable. The rule below is the only route, not the better of two options.

Meanwhile Vehicle is threaded through six intrusive pointers (next, previous, first, last, and the shared-order pair) and two hash chains that store Vehicle ** outright:

Vehicle **hash_tile_prev     = nullptr;  // vehicle_base.h:240
Vehicle **hash_viewport_prev = nullptr;  // vehicle_base.h:237

Rule: VehicleID is the only durable reference. A component reference is valid within one tick phase and is never stored across one. The legacy Vehicle * path stays alive and correct throughout the migration — that is what keeps the game playable between phases.

3. The save format is frozen

This constraint turns out to be the friendly one. SLE_VAR does not use offsetof; it expands to a lambda that returns a member address:

return std::addressof(static_cast<const base *>(b)->variable);
// SLE_GENERAL_NAME, saveload.h:933

The descriptor list is therefore already an indirection layer, keyed by field name — and the "VEHS" chunk is a ChunkType::SparseTable, so pool indices are written explicitly and exact IDs are recoverable on load.

Rule: never touch the descriptor lists. Keep the named fields on Vehicle as a save/load staging area: gather components into Vehicle before saving, scatter back into components after loading. The emitted format is then unchanged by construction — the same fields, names, order and types — vehicle_sl.cpp barely changes, and your benchmark saves keep working. Ignore EnTT's snapshot and continuous_loader entirely; they would write a new format, which is the one thing you cannot have.

Note that preserving the format is a claim about how a given game state is serialised, and is separate from whether two runs produce identical files. They do not, even on unmodified master, for reasons covered under the strategy below.

Check the descriptors, not the comments. Phase 2 assumed sprite_cache was safe to move because it reads as a cache and sits among NOSAVE neighbours — but part of it is serialised for effect and disaster vehicles, which have no engine to regenerate a sprite from. A field's save status is whatever vehicle_sl.cpp says it is, and nothing else. Grep the descriptor lists for every field before moving it.

Strategy: a parallel registry, not a rewrite

Every phase below preserves this division of labour. Vehicle and its pool keep three jobs: identity, cold data, and the save façade. The registry holds hot per-tick data. Loops migrate individually, and both representations stay valid at once during each migration — verified, not assumed.

The technique that makes this safe is shadow mode: when a field moves, write it to both places and assert equality every tick behind a debug flag. You ship the phase with shadow mode on, run your benchmark saves, and only remove the old field once the assert has been silent across a long run. It is the difference between a migration you can trust and one you merely hope about.

Note the deliberate ordering: the early phases are the ones with no determinism exposure, so you learn EnTT's API against systems that cannot desync and are not in the savegame. Risk climbs only after the idioms are familiar.

How a phase proves it changed nothing

This plan originally proposed comparing exit savegames byte for byte. Phase 0 measured that and it does not hold on unmodified master, so it cannot be an exit criterion. Running the same save twice with identical arguments produces exit saves differing in a few hundred bytes. Two observations identify why:

  • One 32-byte cluster is _game_session_stats.savegame_id (misc_sl.cpp:105), a random per-session identifier. Expected, and harmless.
  • The rest are scattered 1–4 byte runs through the VEHS chunk at roughly one per vehicle record — and the count does not grow with run length: 488 differing bytes after 1 tick, 442 after 100, 445 after 20,000.

Divergence that is immediate and does not accumulate is not simulation drift. It points at bytes in the vehicle records that are not a function of game state, most likely fields never initialised for some vehicle types and serialised with whatever the allocator left behind. Ruled out along the way: the link graph never ran, _interactive_random is not saved, and StationCompare orders by index rather than by pointer.

The replacement

A game state fingerprint (src/state_fingerprint.cpp): an FNV-1a hash over the values that define behaviour, split per subsystem. Everything is visited in ascending pool index order, so the hash is a function of the live set rather than of allocation history; and object references are hashed as pool indices, never pointers, so the result is independent of the allocator and of address space layout — which is what lets it survive the very refactors it exists to check.

Splitting it per subsystem is the useful part: a mismatch says where behaviour changed, turning "something diverged" into "vehicles diverged, towns did not".

Verified both directions, because a hash that never changes and one that always changes are equally useless. Two identical 3,000-tick runs give identical fingerprints while their savegames differ by roughly 100 KB — which also confirms the simulation really is deterministic and the savegame noise really is noise. Running 3,001 ticks instead changes the vehicle, company, station and global hashes, and correctly leaves towns and industries alone, because those only update on periodic ticks.

Save format compatibility is untouched by any of this and remains a hard requirement. It is verified differently: a save written by a migrated build must still load in unmodified OpenTTD.

A gap in this, identified while planning phase 6

The fingerprint check runs the same save twice from a fresh load and compares. That catches non-determinism within a run, but it cannot catch an iteration order that depends on session history — both runs start from the same fresh load, so both get the same order.

The missing test is save-resume equivalence: run N ticks then save, reload and run M more, and require the same fingerprint as N+M ticks run straight through. That is the second of the two determinism requirements under constraint 1, and nothing in the harness has been checking it.

Phase 5 implemented it and found it unenforceable. It fails on unmodified code: a game resumed from an autosave-on-exit save does not evolve deterministically — the same binary, given the same exit-save file, disagrees with itself. So the criterion is currently aspirational, and unblocking it is work phase 6 inherits. See phase 5.

The order changed after phase 4

The save staging mechanism was originally the last phase, bundled in as consolidation. It is really infrastructure that phases 4 and 6 depend on, so it became phase 5 and everything after it moved down one. Two things forced it: commit 3 of a field migration is impossible for a serialised field without staging, and every field phase 4 still has to move is serialised — and a view-iterating tick loop cannot show a benefit while it still has to write back to authoritative members on a 560-byte Vehicle.

Incidentally the original order also put a Danger phase before a Caution one, against the risk-ascending principle the rest of the plan follows. The new order fixes that as a side effect.

vcache is now fully migrated: it is not serialised, so its commits 2 and 3 needed nothing from phase 5. It is the first field group to complete all three commits and the first Vehicle member the migration has actually deleted.

An earlier version of this page predicted that finishing vcache would reduce cost rather than add it. That prediction was wrong, and it was wrong because it never named a mechanism. Measurement found neither of the two mechanisms a saving would have needed — see phase 4.

The agreed working sequence

Phase 5, then finish phase 4, then phase 6 running both dispatch variants for comparison. Phases 5, 4 and 6 are all done — and phase 6 ran three variants rather than two, because the second turned out to be two different things wearing one name. Staging needed no staging struct, all nine motion fields are migrated with their members deleted, and the dispatch work that was supposed to pay for that migration paid nothing. Phase 7 is next, and it is now carrying the whole remaining case for this exercise.

That order is forced, not chosen. All nine motion fields are serialised — checked against the descriptor lists rather than assumed: x_pos, y_pos and z_pos at six descriptor sites each, progress at three, direction and tick_counter at two, cur_speed, subspeed and motion_counter at one. Commit 3 is therefore impossible for every one of them without staging, and until commit 3 lands each migrated field keeps paying dual-write cost. No ordering finishes phase 4 before phase 5.

Phase 5 is also the first honest test of whether commit 3 gives anything back. Finishing vcache showed that deleting a member is not automatically a win: its dual writes were cold and its bytes vanished into padding. The motion fields differ on the first count — subspeed and motion_counter are written per tick — so the mechanism absent for vcache is genuinely present here. That makes the two-field commit 3 immediately after staging a cheap, well-isolated measurement. Take it before the bulk work on the other seven groups, not after.

Read the last two columns together, because they disagree

This is not a curiosity, it changes what the later phases aim at. Phase 4 packs hot fields, which helps whatever is walked per part — so the per-part column governs, and trains dominate the part count by an order of magnitude. Road vehicles are the clear second target, taking 28% of the game loop from a fourteenth of the parts. The raw totals hide all of that.

Correction: the first baselines were distorted by asserts

OPTION_USE_ASSERTS is a CMake cache variable and applies to every configuration in a tree, so the original tree had asserts on even in RelWithDebInfo. A second tree configured with OPTION_USE_ASSERTS=OFF was added before phase 3, and it did not merely tidy the numbers — it moved a conclusion.

Assertion checking was more than twice as expensive in road vehicle code as in train code: −36% against −17.5%. So the four vehicle elements were not just inflated, they were inflated unevenly. Per consist, trains turn out to be 2.05× road vehicles rather than 1.6×, and an earlier draft of this page recommended treating them as near equals for phase 6. That was reading assert overhead as vehicle cost.

On Hilbergen the same correction takes trains from 79.7% of the game loop to 70.1%, and the per-part cost that phases 4 and 5 must beat from 116 ns to 85 ns. Chasing the inflated figure would have made any improvement look about a third better than it was.

Fingerprints were identical across both trees on both saves, which confirms asserts do not change game logic — so correctness can be gated in the assert tree while timings come from the release tree. Use build for shadow-mode assertions and the test suite, build-release for any number that goes in a results table.

Registry, identity mapping, lifecycle

ClearDone

An entt::registry now sits beside _vehicle_pool and stays in lockstep with it. Identity maps both ways — a dense std::vector<entt::entity> indexed by VehicleID forwards, and a VehicleRef{VehicleID} component back. No attempt is made to equate entt::entity with VehicleID; version bits make that a trap, and the savegame carries indices anyway. Implemented in src/vehicle_registry.{h,cpp}, and no game data has moved.

Three things the implementation settled that the plan had not:

  • One constructor hook suffices. Pool::CreateAtIndex does ::new (data) T(index, ...), so savegame load arrives through Vehicle::Vehicle like everything else. Destruction hooks into ~Vehicle() above its CleaningPool() early return, so wholesale pool cleaning on new game or load empties the registry too.
  • The registry is a deliberately leaked singleton, following PoolBase::GetPools(). Static destruction order across translation units is unspecified, so a file-scope registry could be destroyed while a Vehicle destructor elsewhere is still running during teardown. Leaking one allocation removes the hazard instead of reasoning about the ordering.
  • Validation had to be split by cost. An O(1) assert on entity count runs at every structural change; the O(n) checks — identity mapping both ways, ascending iteration order — run on demand and are reported as ecs.registry_valid. Per-tick O(n) was not viable: effect vehicles churn constantly so the registry is dirty most ticks, and 85,000 vehicles times 20,000 ticks is not a debug build anyone would wait for.

ClearDone

This was meant to move MutableSpriteCache, colourmap, coord and bounds into components and win on ViewportDrawing. Two things found on contact changed the phase, and both invalidate reasoning that was on this page.

Correction: sprite_cache is not NOSAVE

It is serialised, unconditionally, in two descriptor lists:

SLE_VAR(Vehicle, sprite_cache.sprite_seq.seq[0].sprite, ...)
// vehicle_sl.cpp:1018 in SlVehicleEffect, :1073 in SlVehicleDisaster

Which makes sense in hindsight: effect vehicles (smoke, sparks) and disaster vehicles have no engine to regenerate a sprite from, so the sprite id is game state. That gives it save-format contact, which violates this phase's defining property, so it moves to phase 7 where the staging struct is already on the table.

The sweeps are cold, so the headline win was illusory. ResetVehicleColourMap is called from a company colour change, from company creation and bankruptcy, and from one settings change. ResetVehicleHash comes from afterload.cpp and InitializeVehicles. None of them run from the game loop, so "expect a large multiple on that loop" was true and worthless.

Worse in the other direction: colourmap is a memoisation cache, read by GetEngineColourMap once per vehicle per draw. Moving it behind an accessor adds indirection to the path that actually runs and speeds up one that essentially never does. The phase is perf-neutral by design, not a win — which is a useful thing to have learned cheaply: "move hot fields into components" does not imply "move every NOSAVE field", and a cache read per draw can be better off as a plain field.

What was actually done: colourmap moved to a VehicleColourMap component as the exemplar rather than the whole job. The transferable result is the shape — and the second item is the one that matters:

  • A component holding the data, defaulted so no constructor initialisation is needed.
  • An accessor seam on Vehicle (GetColourMap, SetColourMap, InvalidateColourMap) so the sixteen call sites no longer know where the data lives. This is what makes later phases cheap: storage can move again without touching call sites. All three are const, because a cache is not part of the vehicle's identity — the same reasoning that already made coord mutable. Two const_casts disappeared as a side effect.
  • The sweep as view<T>().each(callback), which uses EnTT's positional fast path for swap_and_pop storage instead of entity indirection.
  • Eager attachment alongside VehicleRef, appropriate because every vehicle needs one. A component only some vehicles need should be emplaced on demand instead.

The sweep is deliberately not sorted, and says so in a comment. Clearing every element is order-independent and the component cannot influence game state — but this is exactly the case where EnTT's reversed walk is visible, so the comment records that nothing may depend on the order.

coord and bounds were attempted and reverted. Both are genuinely presentation-only, so the phase's premise held and the mechanical part went fine. Two things went wrong, and both are worth more than the change would have been.

First, the destructor read a component after the entity was gone. ~Vehicle() calls MarkAllViewportsDirty(), which reads coord, but the phase 1 hook released the entity at the top of the destructor. That is an access violation, not a leak, and it crashed 1.3 seconds into a run. colourmap never exposed it because nothing during teardown reads a colour map. The fix — release the entity last, on both the normal path and the CleaningPool() early return — has been kept, because it is unconditionally more correct for any future component that teardown touches.

Second, and the most important finding of the phase

The accessor seam is only cheap when it is called once per operation. UpdateDeltaXY writes bounds field by field — the road vehicle implementation alone has about fifteen separate writes — and it runs for every moving vehicle every tick. Replacing one field access with a registry lookup per write meant a function call, a vector index, a sparse-set lookup and a dereference, fifteen times where there had been fifteen offsets from this.

Measured on Hilbergen at 20,000 ticks, GameLoop went from 7,971 ms at baseline to 13,874 ms — roughly +74% — in exchange for 24 bytes on a struct. Reverted.

Phase 4 is exactly the same shape. x_pos, y_pos, z_pos, direction, cur_speed and subspeed are all written individually in hot movement code, so a naive accessor per field would reproduce this precisely — and it would be far harder to spot there, because phase 4 is expected to change timings. A 74% regression hiding inside a phase whose purpose is moving timings is the kind of thing that ships.

Also deferred: sprite_cache, as above, which goes to phase 8.

03

Shadow mode

CautionDone

The premise here was "pick the cheapest game-state sweeps first". It does not hold, for the same reason phase 2's did not: every full-pool loop that writes a saved field lives in afterload.cpp or vehicle_sl.cpp, i.e. one-time savegame migration. CallVehicleTicks is the only hot full-pool loop in the game, and converting that is phase 4 and 5 work.

So the phase delivered its durable half instead: the shadow-mode scaffolding, in src/ecs_shadow.{h,cpp}, demonstrated on VehicleCache. That field group was chosen because it is the one that is game-state-affecting but not serialised — cached_max_speed drives movement and cached_cargo_age_period drives cargo ageing, while the single mention of vcache in vehicle_sl.cpp is a read during afterload rather than a descriptor. A genuine Caution target that does not also need the save-staging machinery, which can wait for phase 4.

What shadow mode actually verifies

Not a computation — coverage. Writes still go to the vcache member, with a SyncVehicleCache() after each, and reads go through an accessor that compares the two copies. So if a write site was missed, the component goes stale and the next read reports a mismatch. With 47 usage sites across 9 files, "did I find all 11 writes" is the actual risk.

It counts rather than asserts. An assert stops at the first divergence and tells you only that something is wrong; a counter lets the run finish and reports mismatches against total comparisons, which says how often and therefore usually suggests why. A comparison count of zero is not a pass — it means shadow mode was compiled out, which is the normal state of the release tree.

Known blind spot, found later. Verification only happens where a read goes through the accessor, and the counters are per field group rather than per field — so a field nothing reads that way is never checked while its group still reports clean. That is not hypothetical: a missing sync on cached_vis_effect survived tens of millions of vehicle_cache comparisons. See phase 4.

04

Motion components

CautionDone

The main event, and the reason for the whole exercise. Extract the fields the tick loop actually reads — x_pos, y_pos, z_pos, direction, cur_speed, subspeed, progress, tick_counter, motion_counter — into one or two tightly packed components. This is where the ~600-byte stride collapses toward a cache line.

Resolve the component reference once per function, not once per field access. Phase 2 measured a 74% game loop regression from doing the latter, and the movement code here has the same shape: many individual writes inside one hot function. Bind a local reference at the top and work through it. This is not a micro-optimisation, it is the difference between the phase being a win and being a large loss.

This phase is expected to be slower, deliberately

Phase 3 measured the accessor seam at 2.4% for one small struct read once or twice per vehicle per tick. Nine motion fields, read and written repeatedly through the movement code, will cost more. Moving fields into components does nothing for locality while the loop still walks Vehicle::Iterate() and reaches into the registry per vehicle — the packed walk that pays for it is phase 6's job.

The obvious response is to merge phases 4 and 6 so the net is never negative. That is deliberately not being done. Kept separate, each half is independently measurable: phase 4 answers "what does the seam cost?", phase 6 answers "what does packed iteration buy?". Merged, only the sum is observable, and if the sum disappoints there is no way to tell which half was responsible. The regression is the measurement, not a mistake.

So a slower result here is a pass. What would be a failure is a changed fingerprint, a shadow mismatch, or a regression far outside the predicted range — the last of which would suggest the once-per-function rule was broken somewhere. Prediction, recorded before measuring: scaling phase 3's 2.4% by lookups per vehicle per tick puts this somewhere between 5% and 20% on Hilbergen. Wide, because it depends how many functions in the movement path end up resolving a reference. Well outside that range in either direction means the cost model is wrong, and worth understanding before phase 6 obscures it.

Outcome: the prediction was blown, and the escape clause earned its keep. The full phase landed at +90%, four times the top of the range. Chasing that down — rather than filing it under "phase 4 is expected to be slower" — is what found the real cause, which was three non-inlinable calls per field access and not the seam at all. After repair it sits at +37%. Recording a range in advance is what made the miss visible as a miss; without it, +90% would have been indistinguishable from "the cost we accepted".

Sequence it in three commits per group: add the component and write both (shadow), flip readers over, then delete the shadow write. The Vehicle fields stay declared throughout, because the save descriptors name them; from here they are the staging area described in constraint 3, populated at save time rather than continuously.

What happened: subspeed and motion_counter, commit 1

Measured +9.2% on the Hilbergen game loop, inside the 5–20% predicted range, so the cost model holds. Fingerprints unchanged on both fixtures, shadow mismatches zero, 102 of 102 tests passing. sizeof(Vehicle) rose 544 → 560 while both copies live, as it must.

Two things went wrong and both were caught rather than shipped. 462 shadow mismatches appeared because savegame load writes members straight through the save descriptors' address getters, bypassing every accessor and leaving components stale — fixed with a scatter in AfterLoadVehiclesPhase2. No grep for ->subspeed = could have found that, which is the single strongest argument for shadow mode existing at all. Separately, an early draft read the component and wrote the member in the same expression, which propagates staleness instead of detecting it; the fix was a VerifyMotion() that returns nothing, so a read cannot accidentally come from the shadow copy.

Completing vcache: shadow mode's blind spot, demonstrated

vcache is unserialised, so it went all the way to commit 3 without waiting for staging. Flipping its reads immediately exposed a real bug in the already-committed phase 4 work: UpdateVisualEffect ends with a ToggleBit on the member after its sync call, so the component kept the pre-toggle value indefinitely. Shadow mode had reported zero mismatches throughout.

Zero mismatches is a statement about read coverage, not about the field group

Verification only happens where a read goes through the accessor. cached_vis_effect had no accessor reads, so it had no verification — while the group it belongs to still reported clean, because the counters are per group rather than per field. Only cached_max_speed and cached_cargo_age_period were genuinely covered.

So before trusting a shadow result for a field, check that something actually reads that field through the accessor. The bug was latent rather than live — nothing consumed the stale value — but it would have become a real behaviour change the moment commit 2 flipped the powered-wagon check in train_cmd.cpp over.

What the work did buy is structural rather than numeric: one field group fully migrated, its member gone, its scaffolding retired. That is the shape every remaining group has to follow, and it is now known to work end to end.

Component references survive creation, not destruction

Commit 3 needed a mutable component reference held across a NewGRF callback, which raised the question of when an EnTT reference can dangle. Verified against entt/entity/storage.hpp at 3.16.0 rather than assumed: insertion is safe — assure_at_least grows a paged vector of page pointers, so existing elements never move; removal is the hazard — basic_storage::pop moves the storage's last element into the vacated slot, so destroying some other vehicle can silently turn a held reference into a different entity's data; and sorting relocates elements for the same reason.

So the rule is narrower than "don't hold references": hold them freely across creation, never across vehicle destruction or a registry sort. An initial draft of that code comment said "create or destroy", which was wrong on the create half — worth flagging, because a hazard note that overstates the risk teaches the wrong model just as surely as one that understates it.

All nine fields migrated — and it cost 90%

Every field the phase set out to move is out of Vehicle, in two components: VehicleMotion (cur_speed, subspeed, motion_counter, tick_counter, progress, direction) and VehiclePosition (x_pos, y_pos, z_pos). Grouped by what a hot loop reads together, not by meaning: tick_counter is a generic counter, but CallVehicleTicks reads it in the same few lines as motion_counter, so one lookup serves both. Position is separate because a great deal of code wants coordinates and nothing else.

Each group was gated independently and the fingerprint never moved. sizeof(Vehicle) fell 544 → 528: the first two groups changed nothing, exactly as the padding finding predicted, progress crossed a boundary at 560→552, and position's twelve contiguous bytes did the rest. Small scalars vanish into padding; a large contiguous block does not.

And the game loop went from 6,580 ms to 12,529 ms. Far outside the predicted 5–20% and outside any noise argument — that batch spread 0.3%.

The cause was a deliberate shortcut

Every group was converted mechanically, rewriting each v->x_pos into v->GetPos().x_pos one site at a time. That was chosen on purpose: a per-site rewrite is correct regardless of how v, front, this and consist alias each other in the movement code, whereas hoisting a reference requires proving object identity at every site. Correctness first, across ~850 sites with only the fingerprint as a net.

The bill is what phase 2 measured on bounds: the accessor resolved per access rather than per function. Three opaque calls per field read, none inlinable across translation units — GetVehicleRegistry(), GetVehicleEntity(), then the sparse-set get<T>() — and none of it can be common-subexpression-eliminated because the calls are opaque to the optimiser. direction alone doubled the Debug run, unsurprising at 86 sites plus the sprite path.

Inlining the lookups. VehicleRegistryData moved into the header, the singleton became an extern pointer, and both accessors are now inline. The lazy initialisation was kept — a null check rather than a dynamic initialiser — because the reason for the laziness is a static destruction order hazard, and a namespace-scope initialiser would trade it for a static initialisation order hazard. Caching the entity handle. Vehicle stores its own entt::entity, so component access skips the VehicleID → entity vector lookup. The order of the repair is the transferable part

The instinct is to hoist first, because "resolve once per function" is the rule this page states and phase 2's 74% made memorable. But hoisting is hundreds of edits requiring aliasing analysis at every site, while the constant factor was two header changes. Measuring after the inlining showed it was worth more than every hoist performed afterwards, and it took about twenty minutes.

So the rule needs a qualifier. "Resolve once per function" is right, but it is the second thing to check. First make one access as cheap as it can be: that multiplies through every site whether hoisted or not, and it tells you what the hoisting is worth before you commit to doing it. This phase converted ~850 sites and then recovered half the regression without touching most of them.

The Debug tree got slower at every step of the repair, ending at 272s against 217s before. Not a contradiction — MSVC Debug does not inline, so the change adds call layers there while removing them in release. The clearest justification yet for the two-tree setup: a Debug-only measurement would have rejected the fix that actually worked.

05

The save staging mechanism

CautionDone

Moved forward from what used to be the last phase. It was bundled there as "consolidation", but it is not consolidation — it is infrastructure two later phases depend on. Discovering that is what prompted the reordering.

Constraint 3 explains the mechanism: SLE_VAR(Vehicle, x_pos, …) names a member, so a field cannot leave Vehicle while a descriptor reads it.

No staging struct was needed

The plan called for a staging struct: members mirroring the descriptor names, gathered from components before a save and scattered back after a load. That turned out to be unnecessary, and the simpler answer is strictly better.

SaveLoad holds its address getter as a plain function pointer, and GetVariableAddress const_casts the result before load writes through it. A getter may therefore return the address of anything — including a field inside a component. And SLE_GENERAL_NAME already separates the savegame field name from the member expression used to find it, so the name stays "subspeed" while the storage moves somewhere else entirely.

The result is src/saveload/component_sl.h, three macros wrapping that pattern. Against staging it means no duplicate storage, so sizeof(Vehicle) can actually fall; no gather step, so a field cannot be missed on the way out; and no scatter step, so a component cannot start out stale on the way in — which is precisely the bug that produced 462 shadow mismatches in phase 4. Here it is not possible, because load writes the component and there is nowhere else to write.

Staging is still right when the mapping is not one-to-one: a saved field computed from several component fields, a representation differing between disk and memory, or a component that does not exist for every vehicle. The macros deliberately do not attempt that. The plain case is most of them.

What landed

subspeed and motion_counter are fully migrated, both members deleted — the second and third field groups to complete the three-commit sequence, and the first serialised ones.

Sequencing that mattered: commit 2 flipped only pure reads. Read-modify-write sites were left alone until commit 3, because flipping just the read half of an RMW pair reproduces the exact phase 4 corruption — read the component, write the member, and staleness propagates instead of being reported. In commit 3 the member disappears and the RMW converts atomically, so the hazard never exists.

Commit 3 also turned out to be compiler-verified in a way commit 2 is not: delete the member and every remaining reference is a build error. Thirty-nine of them across seven files, each mechanical. That asymmetry is why the descriptor switch and the member deletion were landed together, and why commit 3 is the cheap half of a migration despite touching more lines.

Correctness: fingerprints unchanged on both fixtures across seven samples, determinism check passing, 102 of 102 tests. Timing: no measurable change — six Hilbergen samples gave a minimum of 7,473 ms against 7,153 ms before, inside the ~7% band, with that batch spreading 9.6% on a visibly warm machine. The mechanism that should have helped is real (DoUpdateSpeed went from two registry lookups per call to one, because SyncMotion() did its own) but is too small to resolve at this noise level.

sizeof(Vehicle) did not move — again

560 in Debug, 544 in release, before and after removing five bytes of fields. This is the second time a removal has been absorbed by padding, so it is a property of the struct rather than a coincidence. Measured offsets after removal: cur_speed 310, acceleration 312, progress 313, waiting_random_triggers 314, random_bits 316, last_station_visited 318, then last_loading_tick at 328 — an 8-byte-aligned TickCounter now preceded by six bytes of padding. alignof(Vehicle) is 8, and the anchors further down (grf_cache 440, sprite_cache 468) did not move at all.

The lesson for the remaining field groups: Vehicle is padding-rich around its 8-byte-aligned members, so removing small scalars does not shrink it. A size win needs a large contiguous block — what phase 8 targets in BaseConsist and sprite_cache — or enough fields removed at once to cross a boundary. The three position fields are 12 bytes together and are the next real candidate. Check with offsetof before predicting.

Savegame compatibility: proven versus argued

The reading half is measured. Both fixtures were written by a stock build; they load in the migrated build and reproduce the baseline fingerprint exactly across seven samples. Since subspeed feeds both the fingerprint and the trajectory, a descriptor reading into the wrong place could not produce a matching 20,000-tick fingerprint.

The writing half is argued from the macro expansion, not measured, because there is no stock build in this tree to load the output. The argument is narrow enough to be solid: the expansion produces a SaveLoad with the same name, type, command and version range as the SLE_VAR it replaced, and only address_func differs — and the writer derives the field table from exactly those members. That is a statement about literal macro expansion rather than about behaviour, which is why it is acceptable here. It is still weaker than a load test, and a stock binary should be kept around to close it.

The save-resume check could not be built, and that is a finding

Standard criterion 4 was implemented as -CheckResume and does not work. It fails on unmodified code. Chasing that down produced something more useful than the check:

  • Runs from the curated fixtures are perfectly deterministic — Hilbergen at 20,000 ticks has reproduced the same fingerprint on every sample ever taken.
  • Runs from an autosave-on-exit save are not. Loading one fixed exit-save file and running 1,000 ticks three times in the same binary gave C3D46F481F656B66, C3D46F481F656B66, 7DBAF9A059E04D46.

Confirmed against a build predating any component work, so it is pre-existing. A game resumed from an exit save does not evolve deterministically at all, which makes the comparison meaningless — and the first diagnosis, "the exit save is not tick-precise", was wrong: tick precision would not fix indeterminate content. This is very likely the same root cause as the phase 0 finding of a few hundred unexplained VEHS bytes: uninitialised state serialised, then fed back on load. That remains a hypothesis — what is measured is the instability, not its source.

A single differing sample is not evidence

The first crossload comparison looked exactly like phase 5 breaking the round-trip: same input file, different fingerprint from the control build. Three more runs showed the same binary disagreeing with itself. The straight-run fingerprints had earned trust over many samples; the resume path never had, and reading one sample from it as a regression would have sent the whole phase chasing a bug that was not there.

Why this has to come before the tick loop is converted

Commit 3 of a field migration — deleting the member — is impossible for a serialised field without this. And every field phase 4 still has to move is serialised: progress, cur_speed, direction and the three position fields. So phase 4 cannot finish until this lands, and until it does every migrated field stays in dual-write mode paying the cost phase 4 measured.

More sharply: phase 6 cannot demonstrate its benefit until commit 3 is done. A view-iterating tick loop reads packed components, which is the point — but while the members are still authoritative it must also write back to them, and that write-back touches the scattered 560-byte Vehicle for every entity. That is exactly the access pattern the packed walk exists to remove. Converting the loop first would measure packed reads plus scattered writes plus dual-write overhead, and produce a number that means very little.

The narrow de-risk experiment, and why it is being skipped

vcache's commit 3 needed no staging and is now done: the member is gone and the component holds the only copy. It is also read-only in the tick loop, so a view over it could be walked with no write-back at all — a narrow but clean early measurement of whether packed iteration pays off. That experiment was previously the recommended next step, on the reasoning that the ordering argument for staging-before-loop-conversion is an inference, and this page's inferences have a poor record next to its measurements.

Decision: skip it and proceed with staging. Two reasons, both better than the argument for doing it. First, the ordering argument stopped being merely inferred — all nine motion fields are now confirmed serialised against the descriptor lists, so commit 3 is blocked for every one of them regardless of what a locality experiment shows. Staging is on the critical path either way, and a null result would not have saved the work. Second, vcache is a weak probe: its reads are two fields out of a 6-byte struct, so a packed walk has almost no data to be dense about. The asymmetry runs badly — a null result would be weak evidence against phase 6, while only a positive result would have told us much. Spending time on a test that can mostly only fail to inform is the wrong trade when phase 6 measures both dispatch variants directly and definitively.

The de-risking effort is better spent on the sort-frequency measurement described under phase 6, which is cheaper still and answers a question that actually gates a design decision.

Exit criteria a save written by the staged build loads in unmodified OpenTTD; subspeed and motion_counter deleted from Vehicle with their shadow mode removed; the resulting sizeof(Vehicle) and timing change recorded.

Temper the expectation with what finishing vcache measured: deleting a member is not automatically a timing win. It gives back the dual-write cost only where those writes were hot, and it shrinks sizeof(Vehicle) only if the bytes were not already absorbable as padding. The motion fields are written per tick, so the first mechanism is genuinely present here in a way it was not for vcache — but the second still needs an offsetof check rather than an assumption.
06

Devirtualising the tick dispatch

DangerDone

Result: the phase that was supposed to pay for phase 4 paid nothing

Three variants were built and measured against each other, interleaved run for run. Devirtualising the dispatch is worth zero. Typed passes are worth −4%. The only configuration that improved anything did so by deleting a correctness property rather than by exploiting the ECS layout — and only on one of the two fixtures.

Everything below the first two sub-headings was written before the measurements and is kept as written, because the gap between the prediction and the outcome is the most useful thing this phase produced.

This is where phase 4 gets paid for. Phase 4 moves the fields and accepts a regression; this phase converts the loop to iterate views, so the registry lookup is amortised across a packed walk instead of repeated per vehicle. Judge the two together as well as separately — the pair is only worthwhile if this phase's gain exceeds phase 4's loss, and knowing both halves is the whole point of having run them apart.

The bill is now known: +37% on Hilbergen, +22% on wentbourne. That is what a packed walk has to beat for the pair to be worth having. It is a real target rather than a guess, and it is a fair one — the self-inflicted part of phase 4's cost has already been repaired, so what remains is genuinely the seam this phase exists to remove.

Replacing virtual bool Tick() plus switch (v->type) with typed passes is the largest structural win available — and it forces a decision you should make deliberately, because the two options differ in kind, not degree:

  • Variant A, order-preserving. One pass in ascending VehicleID, replacing virtual dispatch with a type tag and a switch. Smaller win; the fingerprint still matches the baseline.
  • Variant B, typed passes. Four separate views, one per vehicle type. Much better locality and branch behaviour — but it changes the interleaving of Random() draws, so the fingerprint will change and a save made by stock OpenTTD will no longer continue identically. The format still loads perfectly; the trajectory diverges.

Per-consist cost is the measure that governs here: on the corrected asserts-off baseline that is 4061 ns for trains against 1986 ns for road vehicles, so trains lead on both denominators and are the clear first target. Road vehicles remain a worthwhile second — 28% of the game loop from a fourteenth of the parts — but by a factor of two, not the near tie the assert-enabled numbers implied.

Both variants will be built and A/B'd against the same save. That is the plan, and the comparison is the most interesting single measurement left in the project: the gap between them is a price tag on the determinism constraint itself — the thing constraint 1 says the codebase cannot give up. Very few projects get to measure what their hardest invariant costs them.

Variant B is not merely "different from master" — it is not self-consistent

An earlier draft of this page understated this, and the distinction changes what variant B may be used for. An unsorted EnTT view walks the packed array, and packed order is a function of history, not of the live set — pinned by a test rather than assumed, in entt_smoke.cpp's "default storage order is history dependent". The consequence is divergence not just from stock OpenTTD but from itself:

  • Play to tick N and keep going: packed order reflects the session's whole create/destroy history.
  • Play to tick N, save, quit, reload, keep going: the registry is rebuilt from the pool in ascending index order, so packed order is fresh.

Same savegame, same live vehicles, two different visit orders, two different futures. That breaks save-resume equivalence — the second of the two determinism requirements — and would desync a multiplayer join instantly, because a joining client builds its registry fresh from the transferred savegame while the server carries its accumulated order.

The existing determinism check cannot catch this

The harness runs the same save twice and compares fingerprints. Both runs start from the same fresh load, so both get the same order and the check passes — variant B would look clean.

So phase 6 needs one more tool, and building it is part of the phase's cost: a save-resume equivalence check. Run N ticks then save, reload and run M more; separately run N+M straight through; compare final fingerprints. Variant A must match. Variant B will not, and that failing check is the phase's evidence rather than a bug to chase.

Phase 5 tried to build this and could not — it fails on unmodified code, because a game resumed from an autosave-on-exit save does not evolve deterministically. So phase 6 inherited three pieces of work, in order: answer the uninitialised-state question (a tick-precise save of indeterminate content would still not reproduce); add -vnull:save_at=N to the null video driver, since autosave-on-exit fires at process exit rather than a tick boundary; and only then wire the check up as variant A's gate.

Descoped, deliberately. All three were dropped: phase 6 gates on the fingerprint checks every phase so far has used. This is a measurement fork rather than a shippable branch, and the check would have cost a tick-precise save plus the uninitialised-state investigation to produce evidence for a property that can be argued from the code and is already pinned by a unit test. What is lost is real and is stated here so nobody later mistakes it for a strong guarantee: variant A's order preservation now rests on the fingerprint alone.

And phase 6 then demonstrated exactly why the gap matters. Variant C abandons canonical order outright — and reproduced its own fingerprint perfectly across five runs, passed all 102 tests, and reported registry_valid 1. Every check on this page says it is clean. It is not. Nothing in the harness looks at the one thing it breaks.

Given that, variant B is scoped as a measurement branch, not a foundation. Nothing gets built on top of it and phase 7 continues to target variant A. It is playable single-player — a player cannot observe that resuming produced a different future — which satisfies the ground rule, but it is not a base for further work.

Variant A has its own risk, and it is worth pricing first

Variant A gets locality only if the storage is actually sorted; iterating the pool and looking up components per vehicle is what the code does now, and phase 4 measured that at no locality benefit. So variant A means SortVehicleRegistry() running whenever the registry is dirty — O(n log n) on the live set, around 1.4 million comparisons per sort on wentbourne. It is correct and deterministic, so this is purely a cost question, and the cost depends entirely on how often the dirty flag fires. Rare structural churn amortises to nothing; churn every few ticks could swamp the locality win outright and make variant A pointless.

Measure that first. Instrument SortVehicleRegistry() with a call count and accumulated time, emitted as ecs.sorts and ecs.sort_ms. One wentbourne run then says whether variant A is viable at all — an hour's work that could change the whole shape of the phase, and this page's record is that the cheap measurement beats the confident argument.

If the sort does dominate, the honest options are to accept pool-order iteration with no locality win (variant A becomes just devirtualisation, still worth something), or to note that canonical order and packed locality are fundamentally in tension here and let variant B's number speak to what that tension costs. Both are legitimate results; neither is a failure of the phase.

Sorting the key storage is not sorting the registry

Found while instrumenting, and it would have quietly cost the phase its headline. registry.sort<VehicleRef>() orders the VehicleRef storage and nothing else — the components are separate sparse sets with their own packed arrays, so a view over VehicleMotion would have walked them with no locality at all, which is the entire point of variant A. Matching them is sort_as, one linear pass per storage, and it adds about half again on top of the key sort.

The trap worth recording: a component added at registration and forgotten in the sort is not a correctness bug — nothing iterates a component storage for game state yet — but it silently costs the locality the phase exists to buy. No test catches that, and the fingerprint cannot: the order is right, the data is right, only the layout is wrong.

One more result from the same instrumentation, kept because of its shape. The array is nearly sorted, which is the textbook case for insertion sort over introsort — EnTT takes the algorithm as a parameter, so it is a one-word change. On Hilbergen it was 5.3× faster. On wentbourne it was 16.8× slower, because swap-and-pop moves the last element into each hole and one destruction in an 85,000-element array displaces an element by up to 85,000 positions. Left as std_sort. The optimisation that is obviously right for the fixture you are iterating on can be catastrophic on the one you are not.

The change was verified in the disassembly rather than assumed: the control's call qword ptr [rax+70h] became a jump table with six direct tail-jumps.

The drift control caught a false positive

The control's fastest Hilbergen run came in at 9,010 ms against variant A's 9,221 — a clean-looking 2.3% regression, and exactly the sort of figure that gets written down. But that run also had the fastest landscape and the fastest economy, both byte-identical code in the two binaries. The machine was fast, not the code. The untouched accumulators are not a sanity check, they are the denominator.

Variant B is deterministic after all, and the section above is wrong about why

"Not self-consistent" is true only if the sort is dropped. Variant B as built keeps SortVehicleRegistry() and sorts the typed storages with everything else, so each pass runs in ascending VehicleID — an order that is a pure function of the live set, exactly like PoolIterator. It reproduced AB556BAEFF70ABE4 across five Hilbergen runs and 18AA2463FDF40C94 across both wentbourne runs.

So there are two variant Bs and this page conflated them. B-sorted breaks continuation of a stock savegame and nothing else. B-unsorted — variant C below — is the one that is genuinely not save-resume equivalent, and it is also the only configuration in the phase that removes a cost rather than adding one.

Variant C looks completely clean and is not

It reproduced 87AFB8A437E2B2F1 across five Hilbergen runs and 9FA63EFAD65E1545 across both wentbourne runs, passed 102 of 102 tests, reported registry_valid 1, and its exit save loads and runs in a variant A binary. Every check this project has says it is fine.

It is fine only because every run starts from the same fresh load and therefore evolves the same packed order. The thing variant C actually breaks — that a resumed game continues on a different trajectory than one played straight through — is invisible to all of it, including the fingerprint. This is the save-resume gap, no longer hypothetical.

Worth its own line: the regression suite does not notice variants B or C at all. A change that alters the trajectory of every savegame in existence passes regression, stationlist, gs and gs_compat without a murmur. A green test run is not evidence that behaviour is unchanged.

What the three variants together say

  • Devirtualising the dispatch is worth nothing (A). A switch on a type tag is an indirect branch, same as the vtable it replaced.
  • Typed passes are worth something only for rare types (B). Aircraft gained 11% and trains lost 5% — and trains are 88% of the pool.
  • The ordering discipline is the one real cost, and only on high-churn saves (C). Removing it is worth 8.9% on Hilbergen and nothing on wentbourne.

The uncomfortable conclusion is that the largest single win available in this phase came from deleting a safety property rather than from anything the ECS layout provides. The packed walk, the typed views, the devirtualised dispatch — the entire thesis of phase 6 — contributed nothing measurable or worse.

There is a cheaper way to get most of it that keeps determinism, and this phase did not pursue it: the sort currently redoes O(n log n) over the whole live set every time one smoke puff appears. Inserting the handful of new entities in place would target the same 963 ms without giving up canonical order. That is a fix to the sort rather than to the tick loop, and on the Hilbergen evidence it is worth more than everything phase 6 tried.

A caveat that bounds all of the above

Variants B and C diverge from A at tick one, so after 5,000 ticks they are simulating different worlds — different routes, different depot occupancy, different pathfinder work. The comparison is not strictly like for like. Workload counts land reassuringly close (85,259 parts in every wentbourne run), and the large effects reproduced across pairs, but the 1.1% on road vehicles should not be quoted.

This is unavoidable rather than a flaw in the method. Any change that reorders the simulation has no identical trajectory to be A/B'd against. It is the one measurement in this project where the fingerprint gate and the timing comparison are mutually exclusive.

What to leave alone

The consist chain

Train logic is intra-consist: it walks First() and Next() constantly. ECS buys locality across entities, which is orthogonal to that access pattern. Converting the chain adds indirection and buys nothing.

NewGRF variable resolution

newgrf_engine.cpp alone contains 201 vehicle field reads in a wide switch over variable IDs. It is a cold path per callback, it touches nearly every field, and it is author-facing API surface. Extremely high cost, no measurable gain.

Saveload descriptors

The one thing the ground rules forbid changing. Keep the lists exactly as they are and let the staging struct absorb the layout change.

YAPF and the link graph

Both already have purpose-built data structures — YAPF its own node arena, the link graph its own background job. Different optimisation problems that an ECS does not address.

What to actually expect

Worth calibrating now, so the measurements read as success rather than disappointment.

The draft of this page expected "cheap sweeps to improve dramatically". Phases 2 and 3 found no such sweeps: the full-pool loops are nearly all cold, running on user actions or savegame load rather than per tick. The only hot full-pool loop is CallVehicleTicks, so the whole win has to come from there.

And the accessor seam has a measured price. Phase 3 moved one small struct behind one and cost about 2.4% on Hilbergen — a registry lookup per vehicle per tick. Phase 4, moving nine hot fields, cost +37% after repair and +90% before it. So a phase that adds accessors without also converting the loop to iterate views will lose, and lose big. Expect the gains to come from packed iteration and devirtualised dispatch, not from relocating fields.

A corollary worth internalising, because it was learned the expensive way: most of that 90% was not the seam at all. It was three non-inlinable function calls per field access, fixed by two header changes. Before concluding that an abstraction is inherently costly, check whether the compiler can actually see through it — the architectural cost and the constant factor look identical in a profile and have completely different fixes.

Be disciplined about noise, and note that it is not uniform

Within a batch Hilbergen looks precise; across batches it is not. Two earlier figures on this page were both wrong. A 15% band, measured with compiles running in parallel, was badly pessimistic and would have dismissed a real regression as noise. The 0.3% that replaced it was badly optimistic: it came from a two-sample batch, and two samples cannot estimate a spread — they produce exactly one gap, and a small gap reads as precision when it is really one draw. Eight consecutive runs of an unchanged binary spanned 6.8%.

Each batch is internally tight (0.5–0.9%) but batches sit at different levels, consistent with thermal state and background activity drifting over minutes. So tight-within-batch is not evidence of precision. The working rule: at least five samples, compare minima rather than medians (the minimum is the least-contaminated sample; a median tracks the batch's thermal level as much as the code), discard the first run after a build, and treat anything under about 7% on Hilbergen as unproven. To do better, interleave A and B rather than taking more samples of each — batch drift is the dominant term, and only interleaving cancels it.

There is a cheaper trick, and it works on a single sample: compare against a subsystem you did not change. Every run reports trains, road vehicles, ships and aircraft separately, so if a change touched only aircraft code, the other three are a measurement of the machine. Hoisting the aircraft accessors showed −4.0% on the game loop — which reads as a solid win until you notice trains and ships, both untouched, moved −3.5% and −4.6%. Netted against those controls the real effect was about −8–9% on aircraft and nothing at all on road vehicles. Pick a fixture that exercises what you changed and something you didn't, and read the difference between them rather than the absolute numbers.

But long runs are much noisier than short ones, which inverts the usual intuition. wentbourne takes three and a half minutes and repeats to only 10%, climbing monotonically across consecutive runs in a way that looks like thermal throttling. So use short runs for precision and long runs for coverage, take three samples and a median, discard the first run after a build, and interleave A/B samples rather than running all of one and then all of the other.

One more lesson, added after phase 6 because it is the one that keeps recurring: every confident structural claim on this page has lost to measurement, and every cheap measurement has beaten a confident argument. The virtual call was a textbook target worth nothing. The packed walk was the whole thesis and cost 4%. The sort was assumed to amortise away and costs 10% on one fixture and 0.14% on the other. The insertion sort was obviously right and was 17× wrong. In each case the code reading was reasonable and the answer was elsewhere — usually in a constant factor, a branch predictor, or a property of the savegame rather than of the program.

And for a learning fork, the most valuable outcome is not in any of those columns. Applying ECS to a hostile real-world codebase — one with a shared RNG, a frozen wire format, a save compatibility guarantee stretching back twenty years, and a thousand raw pointers — teaches you far more about where the model actually earns its keep than any greenfield project can. The constraints are the curriculum.
