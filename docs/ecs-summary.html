What the ECS migration actually cost

Seven phases of moving OpenTTD's hottest data into an EnTT registry, measured at every step — and what the numbers say about going further.

Scope phases 0–6, complete Fixtures 2 savegames, 2 build trees Full detail the migration plan

The short version

The registry works, the game is correct at every step, and the savegame format never moved. But the performance thesis did not survive contact with measurement. The tick loop is slower than when we started, the structural win is eight bytes, and the phase specifically designed to pay back the earlier cost paid back nothing.

Phase 6 was the test, and it is the answer

Everything before phase 6 was investment: moving fields out of Vehicle and accepting a regression on the promise that a packed, devirtualised tick loop would pay it back. Phase 6 built that loop three different ways and measured each against the others, interleaved run for run. This is the whole case for the architecture, tested directly.

0%

Devirtualising the dispatch

Replacing the virtual call with a switch on a type tag changed nothing measurable on either fixture. The disassembly says why, and it invalidates the premise: a switch on a type tag is itself an indirect branch. The indirection was relocated, not removed — and against a tick body costing roughly 550 ns per vehicle, neither form is visible.

−4%

Typed passes over packed storage

The gain turned out to be proportional to how rare a vehicle type is, and the cost lands on the common one. Aircraft — 1,529 parts scattered through 85,259 — gained 11%. Trains, at 88% of the pool, lost 5%, because the old loop was already dense in trains and the typed pass buys nothing there.

Weighted by where the time actually is, that is a net loss.

+9%

Abandoning canonical iteration order

The one configuration that improved anything. Keeping the registry sorted — which is what preserves deterministic simulation — costs 10.4% of the game loop on the small fixture and 0.14% on the large one. Dropping it recovers exactly that, so the win is 9% on one fixture and nothing on the other.

It is also unshippable: it breaks the guarantee that a resumed savegame continues identically, which is what makes multiplayer joins work.

And the checks would not have told us

The unshippable variant reproduced its own fingerprint perfectly across five runs, passed all 102 tests, and cross-loaded its savegames cleanly. Every check the project has says it is fine. It is fine only because every run starts from a fresh load; the thing it breaks is invisible to all of them.

Why it did not work

Four reasons, in rough order of how much they matter. None of them is a criticism of EnTT, which did everything it claims to do.

  • The work per vehicle dwarfs the layout. A vehicle tick costs around 550 ns: pathfinder entry, chain walking, NewGRF callbacks, order processing. A cache miss is on the order of 100 ns. Memory layout is one term in that sum and never was the dominant one.
  • OpenTTD had already built the good half of an ECS. Its object pool is a slotmap — stable integer handles, O(1) lookup, dense iteration in ascending index order. The locality an ECS promises was largely already there, so the registry added a sparse-set indirection on top of an already-dense structure. There was far less headroom than the design assumed.
  • Determinism imposes a tax with no counterpart in the old design. Canonical iteration order is free in a slotmap and costs an O(n log n) sort in a registry — up to 10.4% of the game loop. That is a cost the ECS introduces and the pool never paid.
  • The constant factor looked exactly like an architectural cost. The +90% spike was mostly three non-inlinable calls per field access, and two header changes removed most of it. In a profile, "this abstraction is inherently expensive" and "the compiler cannot see through this" are indistinguishable, and they have completely different fixes.

Should the refactor continue?

Not in its current form. The strategy of relocating hot data into components has now been measured end to end, and it loses.

That verdict is specific, not general. What failed is a particular bet: that packed iteration and devirtualised dispatch would beat a well-built slotmap on a workload whose per-item cost is dominated by branching logic rather than by memory access. Phase 6 tested that bet three ways and it lost three times. Continuing to move hot fields would be spending effort against a hypothesis that has already been falsified on this codebase.

What is still worth doing

Two things, and neither is more of the same:

  • Fix the sort rather than delete it. The registry currently redoes a full O(n log n) sort every time a single smoke puff is created. Updating it incrementally instead would target the same 10.4% while keeping the determinism guarantee intact. On the evidence, that one change is worth more than everything phase 6 attempted.
  • Target optional data, not hot data. Every vehicle part carries 88 bytes of consist data that is only meaningful on the 16% of parts that lead a consist — roughly 6 MB of dead weight on the large fixture. Data that only some entities need is the case where component storage genuinely earns its keep, and the win there is memory footprint rather than iteration speed.

Worth being honest about the second one: a side table keyed by vehicle ID would deliver that win too, without a registry. The remaining case for EnTT is ergonomic rather than architectural, which is a much smaller claim than the one this migration set out to prove.

What was worth the trouble anyway

The measurement discipline outlived the hypothesis, and it is the transferable part.

Every confident structural claim in this project lost to measurement, and every cheap measurement beat a confident argument. The virtual call was a textbook optimisation target worth nothing. The packed walk was the entire thesis and cost 4%. The sort was assumed to amortise away and costs 10% on one savegame and 0.14% on another — the small one being the expensive one, which no amount of reasoning about O(n log n) would have predicted. Swapping in an insertion sort was obviously correct and was 17× wrong on the other fixture.

In every case the code reading was reasonable and the answer was somewhere else: in a constant factor, a branch predictor, or a property of the savegame rather than of the program. A hostile real-world codebase — with a shared RNG, a frozen wire format, a twenty-year save compatibility guarantee and a thousand raw pointers — teaches that far better than a greenfield project can. The constraints were the curriculum.
